# STEP 7 Spec で小さなツールを完成させる（90分×2回）

## この回の目的

- STEP 6 の要件をもとに、**設計 → タスク → 実装** まで Kiro と進め、動くツールを完成させる
- できたものを受け入れ条件で確かめ、**main に取り込む（マージ）** ところまで通しで体験する

> 作るのは「変更依頼一覧ビューア」です。ブラウザで開くだけで動く HTML ファイル1枚なので、インストールは要りません。
> **プログラムが読めなくても大丈夫です。** 判断するのは「要件どおりに動くか」だけです。
> この回で、[STEP 6 の表](06-spec-requirements-pr.md#kiro-の-spec-機能が-sdd-そのもの) の残り（設計 → タスク → 実装 → 受け入れ条件で確認）を行い、SDD をひと通り終えます。

---

## 前半（1回目・90分）：要件を直して、設計とタスクを作る

### 1. レビューコメントを要件に反映する（20分）

1. ブランチが `practice/自分の名前` であることを確認し、**Pull** する
2. STEP 6 で Kiro に出させて保存した `participants/自分の名前/review-comments.md` と、GitHub の自分のプルリクエストに自分で付けたコメントを読む
   - 仲間にレビューしてもらった場合は、そのコメントも読む
3. Kiro のチャットで、コメントの内容を伝えて直してもらう

   ```
   requirements.md にレビューで次の指摘がありました。反映してください。
   ・（コメントの内容をここに貼る）
   ```

4. 直った内容を確認したら、GitHub の自分のコメントに「反映しました」と返信する（返信欄の **Reply...** に書いて **Comment**）

### 2. 設計を作る（25分）

1. Kiro パネルの **Specs** 欄から自分の Spec（`change-request-viewer-自分の名前`）を開く
2. `requirements.md` を開き、チャットで次を送る

   ```
   要件を確認しました。設計に進んでください。
   ```

   - 画面に「設計に進む」などのボタンが出ている場合は、それを押しても同じです
3. `design.md` ができたら読んでみる。全部分からなくて大丈夫です。次の3点だけ確認しましょう
   - 画面のイメージ（何がどこに出るか）が書かれているか
   - **ファイルの置き場所が `participants/自分の名前/` になっているか**（`structure.md` のルール）
   - 要件にないものが勝手に増えていないか
4. 分からないところは、そのまま質問する

   ```
   design.md の「○○」の部分を、プログラムを知らない人向けに説明してください。
   ```

### 3. タスクを作る（20分）

1. 設計に納得したら、チャットで「タスクに進んでください」と送る
2. `tasks.md` ができます。作業が番号付きのチェックリストになっていることを確認する
3. タスクが多すぎる（10個を超える）場合は「練習なので、タスクを5〜7個にまとめて」と頼む

### 4. コミット・プッシュ（10分）

1. チャットで「今の変更をすべて『変更依頼一覧ビューアの設計とタスクを作成』というメッセージでコミットして、プッシュしてください」と頼み、表示されたコマンドを確かめて許可する
2. GitHub の自分のプルリクエストを開き、`design.md` と `tasks.md` が増えていることを確認する（同じブランチにプッシュすると、プルリクエストに自動で追加されます）

### 5. 前半のふりかえり（15分）

- 要件 → 設計 → タスクと分けたことで、何が分かりやすくなったか
- 人が書く設計書と比べて、どう感じたか

## 後半（2回目・90分）：実装して、動かして、マージする

### 6. タスクを実行する（30分）

1. ブランチを確認して **Pull** する
2. `tasks.md` を開く（Kiro パネルの **SPECS** で自分の Spec を選ぶか、`.kiro/specs/…/tasks.md` を開く）
3. 画面は次のようになっています。

   ```text
   【tasks.md の画面】
   ──────────────────────────────────────────────────────
    1 Requirements > 2 Design > 3 Task list  Sync Files  [Run all tasks]
                                                         ↑ 押さない
   ──────────────────────────────────────────────────────
    # Implementation Plan

      ⚡ Start task      ← ここを押す（小さな灰色の文字）
    - [ ] 1. HTMLファイルの土台を作る

      ⚡ Start task      ← 1. が終わったら、次はここ
    - [ ] 2. CSVを読み込んで表に表示する
      ...
   ```

   - 上の帯の紫色の **「Run all tasks」は押しません**（全タスクをまとめて実行するボタンです）
   - 各タスク（`- [ ] 1. …` の行）の **すぐ上** に、小さな灰色の文字で **「⚡ Start task」** が出ています。ボタンの形はしていないので見落としやすいです
   - タスクの名前や数は人によって違います（上の図は一例です）
4. **一番上のタスク（1.）の上にある「⚡ Start task」** を押す
   - 右側のチャットで Kiro がタスクの作業を始めます
   - ファイルを書き込む許可を求められたら、**書き込み先が `participants/自分の名前/` であることを確認してから** 許可する
   - 終わると、そのタスクの行が完了の表示（`- [x]`）に変わります
5. 1つ終わったら、次のタスク（2.）の上の「⚡ Start task」を押す。これを最後のタスクまで繰り返す
   - 練習では **1つずつ** 進めて、何が起きているかを見ましょう

> **失敗したら巻き戻せます（STEP 4 で練習済み）。** チャットの履歴には依頼ごとに **チェックポイント** が記録されていて、**「Restore」** を押すとその時点に戻せます。
> 直前の1回分だけ戻したいときは、その依頼のすぐ上にあるチェックポイントの **「Restore」** を押します。

### 7. ブラウザで動かして確かめる（25分）

1. 左側のファイル一覧で `participants/自分の名前/` の中の HTML ファイルを右クリックし、**「Reveal in File Explorer（エクスプローラーで表示）」** を選ぶ
2. エクスプローラーで HTML ファイルをダブルクリックしてブラウザで開く
3. 画面の「ファイルを選択」から `materials/変更依頼一覧_サンプル.csv` を選ぶ
4. `requirements.md` の受け入れ条件を1つずつ見ながら、そのとおりに動くか確かめる
   - 確かめた条件は、メモ帳などに ○ / × を付けておく
5. × があったら、Kiro に伝えて直してもらう

   ```
   受け入れ条件「（条件をここに貼る）」を満たしていません。
   実際には（何が起きたか）になりました。直してください。
   ```

6. 直ったら、ブラウザで **再読み込み（F5）** して、もう一度確かめる

### 8. コミット・プッシュして、最後の見直しをする（15分）

1. チャットで「今の変更をすべて『変更依頼一覧ビューアを実装』というメッセージでコミットして、プッシュしてください」と頼み、表示されたコマンドを確かめて許可する
2. GitHub の自分のプルリクエストを開き、**「Files changed」** タブで、入る予定のファイルを上から眺める
   - `participants/自分の名前/` と `.kiro/specs/change-request-viewer-自分の名前/` 以外のファイルが入っていないか
   - `docs/` や `materials/` を書き換えていないか
3. 問題がなければ、「Conversation」タブの一番下のコメント欄に「実装しました。受け入れ条件はすべて確認済みです。」と書いて **Comment** を押す（あとで振り返るときの記録になります）

> 自分のプルリクエストは、自分では **Approve（承認）できません**。ひとりで進めるときは、手順7の受け入れ条件の確認と、この手順の見直しが「承認」の代わりです。
> 仲間と進めている場合は、仲間に **「Files changed」→「Review changes」→「Approve」** で承認してもらってからマージします。

### 9. マージする（10分）

1. 自分のプルリクエストの下にある **「Merge pull request」** → **「Confirm merge」** を押す
2. **「Delete branch」** ボタンが出ますが、**押さないでください**（STEP 8・9 でもこのブランチを使います）
3. リポジトリのトップ（main）で、`participants/自分の名前/` と `.kiro/specs/change-request-viewer-自分の名前/` が見えることを確認する

#### マージせずに閉じる場合（作ったものを main に入れたくないとき）

やり直したい、作ったものを main に残したくない、といったときは、マージの代わりにプルリクエストを **閉じます**。閉じてもブランチと中のファイルはそのまま残り、STEP 8・9 の作業には影響しません。

1. 自分のプルリクエストを開く（「Conversation」タブのまま）
2. ページの一番下までスクロールする
3. コメント入力欄の右下、緑の「Comment」ボタンの左にある灰色の **「Close pull request」** を押す
4. ページ上部の表示が緑の「Open」から **「Closed」** に変われば完了
   - このあと出る **「Delete branch」** は押さない（STEP 8・9 でこのブランチを使います）

> 開いたままにしておくと、STEP 8・9 で同じブランチにプッシュした変更がこのプルリクエストに自動で追加されてしまいます。マージしないと決めたら、閉じておきましょう。

**おめでとうございます。** 要件定義から実装・レビュー・取り込みまで、AI駆動開発の流れを一周しました。

### 10. 後片付け（5分）

1. 送り忘れがないか確かめる。チャットで次を送る

   ```
   コミットしていない変更や、プッシュしていないコミットはありますか？
   ```

   - 残っていると言われたら、「今の変更をすべて『STEP 7 の残り』というメッセージでコミットして、プッシュしてください」と頼み、表示されたコマンドを確かめてから許可する
2. 自分のプルリクエストが **Merged（マージ済み）** か **Closed（閉じた）** になっていることを、GitHub で確かめる。Open のままなら、マージするか閉じる（上の「9. マージする」）
3. **STEP 8・9 に進む場合：** ブランチ `practice/自分の名前` は **消さずに残します**。Kiro はそのまま閉じてかまいません。次の回の最初に Pull します
4. **ここで終える場合**（STEP 8 以降に進まない）だけ、ブランチを消します

   1. Kiro を終了する（開いたままだと、ブランチを切り替えたときに画面が紛らわしくなります）
   2. PowerShell を開き、次を1行ずつ実行する（`taro` は自分の名前に）

      ```powershell
      cd $HOME\kiro\kiro-handson-practice
      git switch main
      git pull
      git branch -D practice/taro
      git push origin --delete practice/taro
      ```

      | コマンド | 意味 |
      |---|---|
      | `git switch main` | main に切り替える（今いるブランチは消せないため） |
      | `git pull` | main を最新にする |
      | `git branch -D practice/taro` | 自分の PC のブランチを消す |
      | `git push origin --delete practice/taro` | GitHub 上のブランチを消す |

   3. `git branch -a` を実行し、一覧に `practice/自分の名前` が出なければ完了
   - ブラウザで消すこともできます。GitHub のリポジトリで **「Branches」** を開き、`practice/自分の名前` の行の右端のごみ箱アイコンを押します（この場合も、自分の PC のブランチは上の `git branch -D` で消します）
   - マージしたものは main に残っています。閉じたプルリクエストの中身も、プルリクエストの画面から後で見られます

## 困ったとき

- HTML を開いても真っ白 → Kiro に「ブラウザで開くと真っ白です。原因を調べて直してください」と頼む
- 日本語が文字化けする → Kiro に「CSV を開くと文字化けします。UTF-8 と Shift_JIS の両方に対応してください」と頼む
- ファイルが `participants/` 以外にできた → 「作ったファイルを participants/自分の名前/ に移動して」と頼む
- マージボタンが押せない（灰色） → STEP 0 の「main を守る設定」で **Required approvals** を 1 以上にしていないか確認する（Settings → Rules → Rulesets）。ひとりで進める場合は 0 にする
- 完成見本を見たい → [examples/](../examples/) にあります。**自分で作り終えてから** 見比べましょう
