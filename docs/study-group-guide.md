# 勉強会で使うときのガイド（進行役向け）

この手順書は、ひとりで進めることを基本にしています。このページは、**仲間と集まって（またはオンラインで）一緒に進める** ときの、進行役向けの準備と進め方です。
参加者向けの手順は STEP 0〜10 を参照してください。

---

## 1. 全体像

| 回 | 内容 | 時間 | 主な到達点 |
|---|---|---|---|
| 0 | 始める前の準備 | 30〜60分 | Kiro・Git・GitHub がそろい、リポジトリを自分のアカウントにコピーできた |
| 1 | ログインと利用ルール | 30分 | Kiro と GitHub にログインできる |
| 2 | GitHub を見て、Kiro に取り込む | 45分 | GitHub の見方が分かり、クローンして、Kiro にブランチを作ってもらえる |
| 3 | チャットに慣れる | 60分 | 資料を渡して要約・点検させられる |
| 4 | 資料の渡し方と、やり直し方 | 60分 | `#` を使い分け、監督モードで確かめ、チェックポイントの Restore で戻せる。コミット・プッシュを Kiro に頼める |
| 5 | Steering と Hooks | 90分 | 前提説明（Steering）と、自動で動く決まりごと（Hook）を作れる |
| 6 | Spec で要件を作り、見直す | 90分 | requirements.md を作り、PR でレビューし合う |
| 7 | Spec で小さなツールを完成させる | 90分×2 | 実装・動作確認・マージまで一周する |
| 8 | モブ演習 | 90分 | その場で要件を確定する進め方を体験する |
| 9 | 応用：スキルと MCP | 90分 | スキルを作って呼び出し、MCP で外の道具を使える |
| 10 | 上級編：AI-DLC ワークフロー | 45分＋105分 | AI-DLC を入れ、`poc` の型で「質問→文書→承認」を最後まで通せる |

**おすすめの頻度：** 週1回。STEP 1〜3 は1日にまとめて実施してもよい（合計 約2時間15分）。
**人数：** 参加者5〜10名に対し、進行役1名＋サポート1名が目安。STEP 2 と STEP 5 はつまずきやすいので、サポートを厚めにする。

---

## 2. 進め方の基本：一人ひとりが自分のリポジトリで進める

- 参加者は、**それぞれ自分の GitHub アカウントにリポジトリをコピー** して進めます（[STEP 0](00-environment.md) の「5. このリポジトリを自分の GitHub アカウントにコピーする」）
- 1つのリポジトリに全員を集める必要はありません。自分のリポジトリなら、ブランチ・プルリクエスト・マージを自由に練習できます
- **STEP 0 は事前の宿題** にして、初回までに全員が Kiro にサインインでき、自分のリポジトリがある状態にしておくと、当日がスムーズです

### ペアでレビューし合う場合（STEP 6・7）

隣の人とプルリクエストをレビューし合いたいときは、お互いを自分のリポジトリに招待します。

1. 自分のリポジトリの **「Settings」→「Collaborators」→「Add people」** で、ペアの相手の GitHub ユーザー名を入力して招待する
2. 相手に届いた招待（メール、または GitHub の通知）を、相手が **Accept** する
3. STEP 6 のプルリクエストで、右側の **Reviewers** に相手を指定する
4. 相手は自分のプルリクエストの **「Files changed」** で行コメントを付け、STEP 7 では **「Review changes」→「Approve」** で承認する

> 招待した相手は、自分のリポジトリを変更できるようになります。ハンズオンが終わったら、同じ画面から相手を外しておきましょう。
> レビューし合わない人は、手順書どおり Kiro にレビュー役をさせるセルフレビューで進めます。

## 4. 各回の進行のコツ

### STEP 1
- 「入れてはいけない情報」は、具体例を挙げて確認する（例：お客さまの氏名・電話番号・口座番号・問い合わせ内容の原文など）
- クレジットの残量は Kiro のアカウントの表示で確認できる。初回に一度見せておく
- 無料プランの人と有料プランの人が混ざる場合は、STEP 6 以降でクレジットが足りなくなる人が出ることを先に伝えておく

### STEP 2
- GitHub の画面は **見て回るだけ**。ブラウザでのコミットやプルリクエストは扱わない（プルリクエストは STEP 6 で初めて出す）
- 一番つまずく回。**GitHub へのサインイン（Git Credential Manager）** と **フォルダの信頼（Trust）** で止まりやすい
- クラウド同期の対象フォルダにクローンすると同期と衝突することがあるので、避けてもらう
- **公開元ではなく、自分のコピーをクローンしているか**（画面に自分のユーザー名が出ているか）を見て回る
- ブランチ作成を Kiro に頼むのが、**「Kiro がコマンドの許可を求めてくる」最初の場面**。表示されたコマンドを画面に映し、読んでから許可する習慣をここで作る
- 全員のブランチ名が `practice/名前` になっているか、最後に画面左下を見て回る

### STEP 3
- `materials/` のサンプル資料には、議事録と一覧表の食い違いを仕込んである（下記「仕込みの一覧」）。AI がいくつ見つけたか全員で答え合わせする
- 「AI の答えをそのまま使うと危ない例」を1つは出しておく（例：議事録にない期限を AI が補ってしまう）

### STEP 4
- Autopilot のスイッチの位置は版によって変わることがある。事前に進行役の PC で場所を確かめ、画面を映して案内する
- Revert ボタンは Kiro の版によって出ない（2026年10月時点の確認では出なかった）。やり直しはチェックポイントの **Restore** で案内する
- 監督モードの **Reject** と、Autopilot での **チェックポイントの Restore** の違いを表で確認する。「コマンドで変えたもの（コミット・プッシュ）は戻らない」ことを必ず伝える
- 初めてのプッシュでサインインを求められる人がいる。ブラウザで自分の GitHub アカウントにサインインしてもらう
- Kiro が出したコマンドに `main` が入っていないか、最初の1回は隣同士で確かめ合ってもらう

### STEP 5
- Steering を `inclusion: always` で個人の好みを書くと、いつもの答え方が変わってしまう。**個人用は manual** の理由を説明する
- Hook の対象（matcher）が **自分のフォルダだけ** になっているかを必ず確認する。リポジトリ全体が対象だと、資料を読ませるたびに動いて邪魔になる
- ファイルのきっかけ（作成・保存）は **Kiro が変更したときだけ** 動く。手で保存して「動かない」という質問が出やすい
- Kiro が「個人情報は扱えない」と架空の連絡先を書くのを断ることがある。「架空のもので、フックの動作確認のため」と付け足してもらう
- 「自分の業務で毎回やっている確認」を1つずつ挙げてもらうと、Hook の使いどころが伝わる

### STEP 6
- Spec の要件が長くなりすぎる場合は「5個以内に絞って」と頼んでもらう
- **要件まででいったん止める** ことを強調する。設計に進もうとする AI を止めるのも練習のうち
- 完成見本は `examples/requirements-sample/requirements.md`。終わった人から見比べてもらう

### STEP 7
- タスクは1つずつ実行してもらう。全部まとめて実行すると、何が起きたか分からないまま終わる
- 動作確認は **受け入れ条件と1対1で照らし合わせる** のがポイント（人間の仕事は「判断と確認」）
- 完成見本は `examples/change-request-viewer.html`。AI の出力は毎回違うので、見た目が違っていても受け入れ条件を満たせば合格

### STEP 9
- スキルは「必要なときに開く作業手順書」、Steering は「いつも読む業務の説明書」と対比すると伝わりやすい
- 自分のスキルの名前は `request-check-名前` のように名前を入れてもらう（スキルを見せ合うときに区別しやすい）
- MCP の設定は **ユーザー設定（自分の PC だけ）** に入れてもらう。リポジトリの `.kiro/settings/mcp.json` に入れると、そのリポジトリを使う全員に効いてしまうため
- MCP の道具を使う前の許可画面を、全員で一度じっくり読む時間を取る。「何を・どこに送ろうとしているか」を読む習慣をつけるのが目的

### STEP 10
- 前半（準備）でつまずく人が多い。**インストール前に Kiro を完全に終了する**、**フォルダを信頼して Reload Window する**、**新しいチャットごとに aidlc エージェントを選ぶ** の3つを、始める前に画面で見せる
- 前半だけ別の日に行い、`/aidlc --doctor` まで終わらせておくと、後半を余裕を持って進められる
- 有料プラン（Opus のモデルを選べること）が前提。無料プランの人は、画面共有で見学してもらう
- 型は必ず `poc` を指定してもらう。指定しないと `classic`（15段階）などになり、時間内に終わらずクレジットも大きく使う
- 承認ゲートでは「**文書を読んでから** Approve する」を徹底する。読まずに `1` を押し続けると、Spec の「人が判断と確認をする」意味がなくなる
- 段階2（要件分析）では「ファイルに答えを書く」に切り替えてもらう。質問ファイルと `[Answer]:` に慣れておくと、本番の案件で関係者に質問ファイルを回して答えてもらう使い方ができる
- AI の判断で Node.js などを入れようとしたら止める（`technical-environment.md` で禁止している）。コマンドの実行許可の画面をよく読むよう声をかける
- 時間が足りないときは `/aidlc park` で止め、次回 `/aidlc --resume` で再開する
- ふりかえりでは「Spec と AI-DLC のどちらを、どんな案件で使うか」を話してもらう。目安：小さなツールや文書は Spec、関係者が多く経緯の記録が要る案件は AI-DLC

### STEP 8
- 依頼者役は進行役が務めると進めやすい。お題の「依頼者だけが知っている背景」は `exercises/step08-モブ演習のお題.md` の「依頼者役用メモ」にある
- 「あとで考えます」を禁止し、決めるか「未確定事項」にするかを徹底する

## 5. サンプル資料の仕込みの一覧

> 同じ内容を STEP 3 の手順書の最後に「答え合わせ」（折りたたみ）として載せています。演習が終わるまで開かないよう案内してください。

`materials/議事録_サンプル_変更依頼定例.md` と `materials/変更依頼一覧_サンプル.csv` の食い違い：

| 依頼ID | 議事録 | 一覧表 |
|---|---|---|
| CR-2026-012 | 希望リリース日を 12/10 に前倒しで合意 | 希望リリース日が 2027-01-14 のまま |
| CR-2026-015 | 優先度を「高」に引き上げ | 優先度が「中」のまま |
| CR-2026-018 | 取り下げ（依頼部署から撤回の連絡あり） | ステータスが「見積中」のまま |

`materials/ベンダー依頼文_下書き_サンプル.md` のあいまいな点（AI に挙げさせたい例）：
対象画面が特定されていない／「なるべく早く」で期限が不明／「今と同じように」の基準がない／件数・データ量が不明／テスト範囲と受け入れ基準がない／問い合わせ先が書かれていない

## 6. クレジットの目安と注意

- モデルは **Auto（既定）** のままで進めてもらう
- STEP 7 が最も消費が大きい。月の後半に STEP 7 を置く場合は、事前に残量を確認してもらう
- STEP 10（AI-DLC ワークフロー）は Claude Opus 5.5（Auto の 2倍の消費）を使うため、ほかの回より消費が大きい。**月初に置く** のがおすすめ
- STEP 10 が終わったら、モデルを Auto に戻すよう声をかける

---

## 7. 終了後

- 参加者にふりかえり（理解度・仕事で使えそうな場面・つまずいた箇所）を聞く
- ペアで招待し合った人は、Collaborators から相手を外す
