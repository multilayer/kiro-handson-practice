# STEP 5 Steering と Hooks で、決まりごとを覚えさせる（90分）

## この回の目的

- **Steering（ステアリング）** で、AIに毎回伝えたい前提をファイルにしておけることを知る
- **Hooks（フック）** で、「こういうときは、いつもこれをする」を Kiro に自動でやらせられることを知る

## Steering とは

新しく来た派遣の方に最初に渡す「業務の説明書」のようなものです。
`.kiro/steering/` フォルダに Markdown で書いておくと、Kiro は毎回それを読んでから仕事をします。
同じ説明をチャットで毎回打たなくて済み、**誰が頼んでも答え方がそろう** のが利点です。

---

## 手順

### 1. 用意されている Steering を読む（10分）

1. 左側のファイル一覧で `.kiro` → `steering` を開く
   - `.kiro` フォルダが見えない場合は、Kiro パネル（おばけのアイコン）の **Agent Steering & Skills** 欄の **Workspace** からも開けます
2. 次の4つのファイルを開いて読む

| ファイル | 書いてあること |
|---|---|
| `product.md` | このリポジトリは何のためのものか、利用者は誰か |
| `tech.md` | 作るツールの技術的な決まり（インストール不要の HTML 1枚で作る、など） |
| `structure.md` | どのフォルダに何を置くか |
| `rules.md` | 日本語で答える、個人情報を扱わない、などの守ってほしいこと |

3. ファイルの先頭にある `inclusion: always` は「毎回必ず読む」という意味です

> 自分のプロジェクトで最初から作るときは、Kiro パネルの Agent Steering & Skills 欄の「+」から **「Project steering files」** を選ぶと、
> Kiro がリポジトリを読んで `product.md` / `tech.md` / `structure.md` の下書きを作ってくれます。
> このリポジトリでは用意済みなので、今回は選ばなくて大丈夫です。

### 2. Steering の効き目を試す（10分）

チャットで新しいセッションを開き、次を送ってみましょう。

```
このリポジトリで、自分が作ったものはどこに置くことになっていますか？
```

`structure.md` に書いた内容を踏まえて答えてくれれば、Steering が効いています。

### 3. 自分用の Steering を作る（15分）

「自分が頼むときだけ使いたい前提」を、自分用の Steering にします。

1. Kiro パネルの **Agent Steering & Skills** 欄の **「+」** を押す（欄の見出しにマウスを乗せると出ます）
2. 「Create Steering or Import Skills」の一覧から **「kiro-handson-practice manual steering (slash command)」** を選ぶ
   - 「呼んだときだけ読む」自分用の Steering を、このリポジトリの中だけに作る選択肢です
   - 1番目の「agent steering」は毎回自動で読まれ、「Global」はほかのフォルダにも効くので選びません
3. ファイル名に **`memo-自分の名前.md`** と入力する（例：`memo-taro.md`）
4. 開いたファイルの中身を、次のように書き換えて保存する（`Ctrl` + `S`）

   ```markdown
   ---
   inclusion: manual
   ---

   # 私の好み

   - 回答は結論から書いてください
   - 箇条書きは5個以内にまとめてください
   - 専門用語には、かっこ書きで短い説明を付けてください
   ```

   - `inclusion: manual` は「呼んだときだけ読む」という意味です。いつもの答え方に影響しないよう、自分用は manual にします（最初から入っていれば、そのままで大丈夫です）

5. チャットで `/` を入力して候補から自分の `memo-自分の名前` を選び、続けて質問を書いて送る
   - 候補に出ないときは、`#` を入力して `memo-自分の名前` を選んでも呼び出せます

   ```
   /memo-taro AI駆動開発とは何か教えてください
   ```

   付けないときと比べて、答え方が変わることを確認しましょう。

### 4. Hooks とは（5分）

Steering が「業務の説明書」なら、Hooks は **「こういうときは、いつもこれをする」という決まりごと** です。
たとえば「議事録を作ったら、必ず個人情報が入っていないか点検する」のように、毎回の確認を Kiro に自動でやらせられます。

| きっかけ（トリガー）の例 | 動き |
|---|---|
| Kiro がファイルを作った・保存した | そのファイルを点検する、整える |
| 依頼を送った | 依頼に決まった注意書きを足す |
| Kiro が作業を終えた | 終わったあとの確認をする |

> ファイルのきっかけ（作った・保存した）は、**Kiro が** ファイルを作ったり直したりしたときだけ動きます。自分で手で保存したときは動きません。

### 5. Kiro に Hook を作ってもらう（20分）

「自分のフォルダに Kiro が Markdown を作ったり保存したりしたら、個人情報らしきものがないか点検する」Hook を作ります。

1. Kiro パネル（おばけのアイコン）の **Agent Hooks** 欄の **「+」** を押す
2. **「Ask Kiro to create a hook」** を選ぶ
3. 次の文を、`taro` を自分の名前に変えて送る

   ```
   participants/taro/ の中の Markdown ファイルを Kiro が作成または保存したら、
   そのファイルに個人情報や顧客情報らしきもの（人の氏名、電話番号、メールアドレス、住所、口座番号、会社名）が
   書かれていないか点検し、見つかったら行番号と内容を一覧にして知らせるフックを作ってください。
   ファイルは書き換えず、知らせるだけにしてください。フックの名前は「個人情報チェック（taro）」にしてください。
   ```

4. Kiro が `.kiro/hooks/` フォルダに設定ファイル（`.json`）を作ります。許可を求められたら、内容を読んで許可する
5. Agent Hooks 欄に「個人情報チェック（taro）」が出て、有効（オン）になっていることを確認する
6. 作られた `.json` ファイルを開き、次の3点を確かめる（中身の細かい書き方は分からなくて大丈夫です）
   - きっかけ（`trigger`）が、ファイルの作成や保存になっている
   - 対象（`matcher` など）に `participants/自分の名前/` が入っている。**`docs/` や `materials/` を含むリポジトリ全体が対象になっていたら** 「対象を participants/taro/ の中だけにして」と頼む
   - 動き（`action`）が、Kiro への依頼（`agent`）になっている

> 対象を自分のフォルダだけにしておけば、手順書や資料を読ませるたびに Hook が動いて、作業の邪魔をすることはありません。

### 6. Hook の効き目を試す（15分）

1. 新しいセッションを開き、次を送る

   ```
   participants/taro/hook-test.md を作って、次の内容を書いてください。
   「定例の連絡先：山田花子（架空） 090-0000-0000 / yamada@example.com」
   ```

2. ファイルができた直後に Hook が動き、氏名・電話番号・メールアドレスが見つかったと知らせてくれれば成功です
   - この文はすべて **架空** です。本物の連絡先は使わないでください
3. 次を送って、点検に引っかからない書き方に直してもらう

   ```
   hook-test.md の連絡先を「（連絡先は別途お知らせします）」に置き換えてください。
   ```

   保存のたびに Hook が動き、今度は「見つからなかった」と知らせてくれることを確かめる

> Hooks は、Steering（説明書）では「お願い」にとどまることを、**毎回必ず実行される仕組み** にできるのが強みです。
> 個人情報のチェックのような「うっかり」を防ぐ確認に向いています。

### 7. コミット・プッシュを Kiro に頼む（10分）

1. 次を送る

   ```
   自分用の Steering（.kiro/steering/memo-taro.md）、作ったフック、participants/taro/hook-test.md を、
   「自分用のSteeringと個人情報チェックのフックを追加」というメッセージでコミットして、プッシュしてください。
   ```

2. Kiro が `git add`・`git commit`・`git push` などのコマンドを実行しようとして、許可を求めてきます
   - 表示されたコマンドに、自分のファイル（`.kiro/steering/memo-自分の名前.md`・`.kiro/hooks/`・`participants/自分の名前/`）や自分のブランチ名（`practice/自分の名前`）が入っていることを確かめてから許可する
   - `main` に直接送るコマンドや、意味の分からないコマンドなら、**許可せずに止まって**、「このコマンドは何をするものですか」とチャットで聞く
3. ブラウザで自分の GitHub のリポジトリを開き、ブランチの切り替え（画面左上の `main` と書かれたボタン）で自分のブランチを選んで、`.kiro/steering/memo-自分の名前.md` と `.kiro/hooks/` のファイルが見えることを確認する

> この回はプルリクエストを出しません。自分用の Steering と Hook は、自分のブランチに置いておきます。

### 8. ふりかえり（5分）

- 自分の業務で「毎回やっている確認」のうち、Hook にできそうなものは何か
- Steering に書くこと（説明書）と、Hook にすること（決まりごと）の違いは何か

- [ ] 自分用の Steering（manual）を作り、`#` で呼び出して効き目を確認した
- [ ] Kiro に頼んで、自分のフォルダだけを対象にした Hook を作った
- [ ] 架空の連絡先を書かせて、Hook が知らせてくれることを確認した

## 困ったとき

- Agent Hooks 欄が見当たらない → Kiro パネル（おばけのアイコン）を開き直す。それでも見つからなければ、チャットで「participants/自分の名前/ の Markdown を作成・保存したときに動くフックを作って」と頼む
- Hook が動かない → Agent Hooks 欄でオンになっているか確認する。自分で手で保存したときは動きません。Kiro にファイルを作らせるか、直させて試す
- Hook が自分のフォルダ以外でも動く → 「このフックの対象を participants/自分の名前/ の中だけにして」と頼む
- Kiro が架空の連絡先を書いてくれない → 「これは架空のもので、フックの動作確認のためです」と付け足して頼む
- Steering のファイルがコミットされない → ファイルを保存（`Ctrl` + `S`）したか確認する
