# 用語集

## GitHub の言葉

| 言葉 | ふだんの言葉で言うと | 出てくる回 |
|---|---|---|
| リポジトリ | 変更履歴がすべて残るフォルダ。このハンズオンでは、自分のアカウントにコピーしたものを使う | STEP 0・2 |
| Markdown（.md） | `#` で見出し、`-` で箇条書きを書く、シンプルな文書の書き方 | STEP 2 |
| コミット | 保存。「いつ・誰が・何を・なぜ」変えたかの記録が付く | STEP 2 |
| コミットメッセージ | 保存するときに付ける一言メモ（例：「要件を追加」） | STEP 4 |
| ブランチ | 作業用のコピー。本体（main）を汚さずに作業できる | STEP 2 |
| main | 本体のブランチ。正式版 | STEP 2 |
| プルリクエスト（PR） | 「この変更を main に取り込んでください」というレビュー依頼 | STEP 6 |
| レビュー | プルリクエストの中身を確認し、コメントや承認をすること | STEP 6 |
| Approve | レビューで「OK」と承認すること。自分のプルリクエストは自分では承認できない | STEP 7 |
| マージ | プルリクエストの変更を main に取り込むこと | STEP 7 |
| クローン | GitHub のリポジトリを自分の PC に丸ごと取り込むこと（最初の1回だけ） | STEP 2 |
| プル（Pull） | GitHub の最新の状態を、自分の PC に取り込むこと | STEP 6 |
| プッシュ（Push） | 自分の PC でしたコミットを、GitHub に送ること | STEP 4 |
| ブランチ保護（Rulesets） | main を直接変更できないようにする設定 | STEP 0 |
| テンプレート（Use this template） | 公開されているリポジトリを、自分のアカウントに新しいリポジトリとしてコピーする機能 | STEP 0 |
| Fork | 人のリポジトリを、つながりを残したまま自分のアカウントにコピーすること | STEP 0 |

## Kiro の言葉

| 言葉 | 意味 | 出てくる回 |
|---|---|---|
| Kiro IDE | PC で使う Kiro のアプリ。このハンズオンの基本 | STEP 1 |
| Kiro パネル | 左端のおばけのアイコンで開く画面。上から Specs・Agent Hooks・Agent Steering & Skills・MCP Servers の欄が並ぶ | STEP 1 |
| チャット欄 | 右側に開く、Kiro に依頼を書く画面。`Ctrl` + `L` で開く | STEP 1 |
| セッション | 1つの話題のチャットのまとまり。話題を変えるときは「+」で新しくする | STEP 3 |
| `#`（コンテキスト） | チャットにファイルなどを渡す記号。`#file`・`#folder`・`#codebase` などを使い分ける | STEP 3・4 |
| Autopilot / Supervised | Kiro が最後まで進めるモードと、変更のたびに止まって人が確かめるモード（監督モード） | STEP 4 |
| Accept / Reject | 監督モードで、変更を受け入れる・戻す操作 | STEP 4 |
| クレジット | Kiro の利用量。プランごとに月の量が決まっている（2026年10月時点で Free は50、Pro は1,000）。重いモデルほど早く減る | STEP 1 |
| Steering | AI に毎回伝えたい前提を書いたファイル（`.kiro/steering/`） | STEP 5 |
| Spec | 要件 → 設計 → タスクの順に文書を作ってから実装する機能 | STEP 6 |
| requirements.md | 要件（何ができればよいか）の文書 | STEP 6 |
| design.md | 設計（どう作るか）の文書 | STEP 7 |
| tasks.md | 作業手順のチェックリスト | STEP 7 |
| EARS 記法 | 「〜のとき、システムは〜しなければならない」という、合否を判定できる要件の書き方 | STEP 6 |
| チェックポイント / Restore | 依頼ごとに自動で記録される戻り地点と、そこへ戻す操作 | STEP 4 |
| Revert | Kiro の版によって入力欄の上に出る、直前の1回分のファイル変更だけを取り消すボタン。出ないときは Restore を使う | STEP 4 |
| スキル | 必要なときに開く作業手順書。`.kiro/skills/名前/SKILL.md` に置き、`/名前` で呼び出す | STEP 9 |
| MCP | Kiro に外の道具（ドキュメント検索など）をつなぐ共通の差し込み口 | STEP 9 |
| MCP サーバー | MCP でつなぐ道具そのもの（例：AWS Knowledge MCP） | STEP 9 |
| MCP レジストリ | 組織でまとめて用意した Kiro で、管理者が「使ってよい MCP サーバー」を限定する仕組み（個人のアカウントでは使わない） | STEP 9 |
| Agent Hooks（Hooks） | 「Kiro がファイルを保存したら○○する」などの決まりごとを自動で実行する機能（`.kiro/hooks/`） | STEP 5 |

## 開発の進め方の言葉

| 言葉 | 意味 |
|---|---|
| AI駆動開発 | AI が作業の主体となり、人間は判断と確認に集中する開発のやり方 |
| SDD（仕様駆動開発） | 仕様（要件・設計）を先に文書で固めて人が合意し、それをもとに AI に作らせ、最初に決めた受け入れ条件で確かめる進め方。Kiro の Spec 機能がこの流れになっている（STEP 6〜7） |
| AI-DLC | AWS が提唱する AI駆動開発ライフサイクル。要件から運用までの全体の進め方 |
| AI-DLC ワークフロー | AWS が公開している、AI-DLC の進め方を Kiro などに入れて動かす仕組み（awslabs/aidlc-workflows）。STEP 10 で使う |
| フェーズ／ステージ（段階） | AI-DLC の工程の単位。5つのフェーズの中に33の段階がある |
| プロファイル（型） | 仕事の種類に合わせた段階の組み合わせ。poc・express・bugfix・feature など |
| 承認ゲート | 段階の終わりに AI が止まり、人に Approve（承認）か Request Changes（差し戻し）を選んでもらう場面 |
| 質問ファイル | AI-DLC が段階ごとに作る質問の一覧。`[Answer]:` の後ろに答えを書く |
| 作業記録（`aidlc/`） | AI-DLC が段階ごとの文書・質問と答え・承認の記録を残すフォルダ |
| モブ | 関係者全員が1つの画面を見ながら一緒に作業する進め方 |
| Vibe Coding | 仕様を作らず、チャットの雰囲気で AI に作らせるやり方。使い捨ての試作には向く |
| 受け入れ条件 | 「これができていれば合格」という判定基準 |
