# STEP 9 応用：スキルと MCP で Kiro を広げる（90分）

## この回の目的

- **スキル** で「よくやる仕事の手順」を Kiro に覚えさせ、呼び出せるようになる
- **MCP** で Kiro を外の道具（今回は AWS の公式ドキュメント）につなぎ、使えるようになる

> STEP 1〜8 を終えた人向けの応用編です。

## まず違いを押さえる

| 仕組み | たとえると | いつ読まれるか | 置き場所 |
|---|---|---|---|
| Steering（STEP 5） | 新しく来た人に渡す **業務の説明書** | 毎回（または呼んだとき） | `.kiro/steering/` |
| Hooks（STEP 5） | 「こういうときは、いつもこれをする」という **決まりごと** | ファイルの作成・保存など、決めたきっかけが起きたとき | `.kiro/hooks/` |
| **スキル** | 必要なときに開く **作業手順書** | 依頼の内容が合ったとき、または `/スキル名` で呼んだとき | `.kiro/skills/＜スキル名＞/SKILL.md` |
| **MCP** | Kiro に差し込む **外の道具**（USB 機器のようなもの） | AI が道具を使うと決めたとき（使う前に許可を求められる） | 設定ファイル `mcp.json` |

## 前半：スキル（45分）

### 1. 用意されているスキルを見る（10分）

1. ブランチが `practice/自分の名前` であることを確認し、**Pull** する
2. 左側のファイル一覧で `.kiro` → `skills` → `minutes-summary` → `SKILL.md` を開く
3. 先頭の `---` で囲まれた部分を読む

   ```markdown
   ---
   name: minutes-summary
   description: 議事録を「決まったこと・持ち越し・ToDo」に整理し、participants フォルダに保存する。議事録の整理や要約を頼まれたときに使う。
   ---
   ```

   - `name`：スキルの名前（フォルダ名と同じ、半角英小文字とハイフン）
   - `description`：**いつ使うスキルか**。Kiro はこの説明を見て、使うかどうかを決めます
4. その下に、作業の手順と出力の形が書かれていることを確認する

### 2. スキルを呼び出す（10分）

チャットで新しいセッションを開き、入力欄に **`/`** を打つと、スキルの一覧が出ます。`minutes-summary` を選び、続けて資料を渡します。

```
/minutes-summary #materials/議事録_サンプル_変更依頼定例.md
```

- 結果が `participants/自分の名前/` に保存されることを確認する（書き込みの許可を求められたら、場所を確かめてから許可）
- スキルを使うと、**誰が頼んでも同じ形で出てくる** のがポイントです

> `/` を付けずに「この議事録を整理して」と頼んでも、`description` に合えば Kiro が自分でスキルを使います。試してみましょう。

### 3. 自分のスキルを Kiro に作らせる（25分）

ふだんの仕事の中から「毎回同じ手順でやっていること」を1つ選び、スキルにします。今回は例として「ベンダー依頼文のチェック」を作ります。

1. チャットで次を送る（`taro` は自分の名前に）

   ```
   ベンダー依頼文の下書きをチェックするスキルを作ってください。
   場所は .kiro/skills/request-check-taro/SKILL.md です。
   チェック観点は「対象画面・帳票」「期限とその理由」「件数・データ量」「受け入れ基準」「問い合わせ先」です。
   結果は「足りない点」と「書き直し案」の2つに分けて出すようにしてください。
   ```

2. できた `SKILL.md` を開き、`name` と `description` を読む。`description` が「いつ使うか」になっていなければ、直してもらう
3. 新しいセッションを開いて試す

   ```
   /request-check-taro #materials/ベンダー依頼文_下書き_サンプル.md
   ```

4. 思いどおりでなければ、「スキルの手順に○○を足して」と頼んで直す
5. 作ったスキルを保存（コミット）して、GitHub に送る（プッシュ）。チャットで次を送る（`taro` は自分の名前に）

   ```
   .kiro/skills/request-check-taro/ の変更を「依頼文チェックのスキルを追加」というメッセージでコミットして、
   GitHub にプッシュしてください。
   ```

   - Kiro が `git add`・`git commit`・`git push` などのコマンドを実行しようとして、許可を求めてきます
   - 表示されたコマンドに、自分のファイル（`.kiro/skills/request-check-自分の名前/`）や自分のブランチ名（`practice/自分の名前`）が入っていることを確かめてから許可する
   - `main` に直接送るコマンドや、意味の分からないコマンドなら、**許可せずに止まって**、「このコマンドは何をするものですか」とチャットで聞く
   - ブラウザで GitHub を開き、ブランチの切り替え（画面左上の `main` と書かれたボタン）で自分のブランチを選んで、`.kiro/skills/request-check-自分の名前/SKILL.md` が見えれば送れています
   - この回はプルリクエストを出しません

> **ほかの人のスキルを取り込むこともできます。** Kiro パネルの **Agent Steering & Skills** 欄の「＋」→ **Import a skill** から、GitHub 上のスキルや PC のフォルダを取り込めます。人が作ったスキルは、Kiro への指示がそのまま書かれたものです。**取り込む前に必ず中身を読み、何をさせる手順なのかを確かめましょう。**

## 後半：MCP（45分）

### 4. MCP とは（5分）

Kiro は、ふだんはこのリポジトリと Web 検索しか見えません。**MCP（Model Context Protocol）** は、Kiro に外の道具をつなぐための共通の差し込み口です。
今回は、AWS が公開している **AWS Knowledge MCP サーバー**（AWS の公式ドキュメントを検索する道具）をつなぎます。インストールもログインも不要です。

> **注意：** MCP の道具に送った質問は、外部のサービスに届きます。**個人情報・顧客情報・秘密情報を含む質問はしない** でください。
> また、MCP サーバーは誰でも作って公開できます。**提供元が信頼できるものだけ** をつなぎましょう（今回の AWS Knowledge MCP は AWS の公式のものです）。

### 5. 設定ファイルを開く（10分）

今回は **自分の PC だけ** に設定します（リポジトリには入れません）。

1. キーボードで **`Ctrl` + `Shift` + `P`** を押す
2. `Kiro: Open user MCP config` と入力し、**「Kiro: Open user MCP config (JSON)」** を選ぶ
   - Kiro パネルの **MCP SERVERS** 欄にある「設定を開く」アイコンからも開けます
3. `mcp.json` というファイルが開きます

### 6. AWS Knowledge MCP を追加する（10分）

1. ファイルの中身を、次のように書き換える（すでに `mcpServers` の中に別のサーバーが書かれている場合は、消さずに、`"aws-knowledge": { … }` の部分だけを `,` で区切って書き足す）

   ```json
   {
     "mcpServers": {
       "aws-knowledge": {
         "url": "https://knowledge-mcp.global.api.aws",
         "type": "http",
         "disabled": false
       }
     }
   }
   ```

2. **`Ctrl` + `S`** で保存する
3. Kiro パネルの **MCP SERVERS** 欄に `aws-knowledge` が出て、接続済み（緑の印）になれば成功です

### 7. MCP の道具を使ってみる（15分）

新しいセッションを開き、次を送ります。

```
AWS の公式ドキュメントで調べて答えてください。
Amazon Bedrock は東京リージョン（ap-northeast-1）で使えますか？ 根拠になったページの URL も付けてください。
```

1. Kiro が `aws-knowledge` の道具（例：`search_documentation`）を使おうとして、**許可を求めてきます**
2. 何を調べようとしているかを読んでから **許可** する
3. 答えに、AWS のドキュメントの URL が付いていることを確認する

**比べてみましょう：** 設定ファイルの `"disabled": false` を `true` に変えて保存し、同じ質問をすると、答え方はどう変わるでしょうか。

### 8. 後片付け（5分）

1. MCP を使い続けない場合は、`"disabled": true` にして保存しておく（設定は残り、道具は止まります）
2. 送り忘れがないか確かめる。チャットで「コミットしていない変更や、プッシュしていないコミットはありますか？」と聞き、残っていればコミット・プッシュを頼む
3. 練習ブランチを使うのはこの回が最後です（STEP 10 は別のフォルダで進めます）。このブランチから出したプルリクエストが **Open のまま残っていないか** GitHub で確かめ、残っていれば、ページの一番下の **「Close pull request」** で閉じる
4. 練習ブランチを消す

   1. Kiro を終了する（開いたままだと、ブランチを切り替えたときに画面が紛らわしくなります）
   2. PowerShell を開き、次を1行ずつ実行する（`taro` は自分の名前に）

      ```powershell
      cd $HOME\kiro\kiro-handson-practice
      git switch main
      git pull
      git branch -D practice/taro
      git push origin --delete practice/taro
      ```

      | コマンド | 意味 |
      |---|---|
      | `git switch main` | main に切り替える（今いるブランチは消せないため） |
      | `git pull` | main を最新にする |
      | `git branch -D practice/taro` | 自分の PC のブランチを消す |
      | `git push origin --delete practice/taro` | GitHub 上のブランチを消す |

   3. `git branch -a` を実行し、一覧に `practice/自分の名前` が出なければ完了
   - ブラウザで消すこともできます。GitHub のリポジトリで **「Branches」** を開き、`practice/自分の名前` の行の右端のごみ箱アイコンを押します（この場合も、自分の PC のブランチは上の `git branch -D` で消します）
   - マージしたものは main に残っています。閉じたプルリクエストの中身も、プルリクエストの画面から後で見られます

## 困ったとき

- `/` を打ってもスキルが出ない → `SKILL.md` の `name` とフォルダ名が同じか確認する。Kiro を再起動する
- スキルが勝手に使われない → `description` に「〜を頼まれたときに使う」と書き足してもらう
- MCP SERVERS に出ない・赤い印になる → JSON の `{ }` や `,` が崩れていないか確認する。Kiro パネルの **Output** タブで **「Kiro - MCP Logs」** を見る
- 「N servers hidden」と出る → 組織の管理者が使える MCP サーバーを限定しています（組織でまとめて用意した Kiro を使っている場合）。個人のアカウントでサインインしているか確認する
- プロキシのあるネットワークでつながらない → プロキシの設定が必要な場合があります。[STEP 0](00-environment.md) の「6. ネットワーク」を見る
