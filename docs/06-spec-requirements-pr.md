# STEP 6 Spec で要件を作り、レビューを頼む（90分）

## この回の目的

- Kiro の **Spec（スペック）** 機能で、作りたいものの **要件（requirements.md）** を AI と一緒に作る
- 作った要件を **プルリクエスト** にして、AI と自分の目で見直す（セルフレビュー）

> この回は **要件まで** で止めます。設計と実装は STEP 7 で行います。
> 実は、業務部門の要望をまとめて開発会社（ベンダー）に伝える、という仕事に一番近いのがこの回です。

## Spec とは（なぜこれで SDD になるのか）

### SDD（仕様駆動開発）とは

**SDD（Spec-Driven Development／仕様駆動開発）** は、「作る前に、何を作るかを文書（仕様）で決めて合意し、その文書をもとに作り、その文書で確かめる」進め方です。
ポイントは次の3つです。

1. **作る前に**、要件・設計を文書にする
2. その文書を **人が確認して合意してから** 作る
3. できたものを、**最初に決めた受け入れ条件で確かめる**

システム開発で、業務部門の要望を **要件定義書** にまとめ、ベンダーと **設計書** で合意し、最後に **受け入れテスト** をするのと同じ考え方です。SDD は、その「ベンダー」の役を AI にやってもらう進め方だと考えてください。

### チャットとの違い

STEP 3〜5 で使ったチャットは、「頼んだら、すぐ作る」進め方です。小さな作業なら速いのですが、何を作るかが頭の中にしかないので、AI の思い込みで作られたり、後から「なぜこうなったのか」がわからなくなったりします。

```text
チャット：  頼む ──────────────→ できあがり（作る前の合意がない）

Spec   ：  頼む → 要件 → 設計 → タスク → 実装 → 受け入れ条件で確認
                  ↑確認    ↑確認   ↑確認
```

### Kiro の Spec 機能が SDD そのもの

Kiro の **Spec** 機能は、この SDD の流れを画面の操作としてそのまま用意したものです。
Kiro パネルの **SPECS の「+」** から始めると、Kiro が次の3つの文書を **順番に** 作り、**人が確認するまで次に進みません**。

| SDD でやること | Kiro の Spec で作られるもの | このハンズオンでやる場所 |
| --- | --- | --- |
| 何を作るかを決める（要件・受け入れ条件） | `requirements.md` | STEP 6 |
| 要件を人が確認して合意する | プルリクエストで見直す（レビュー） | STEP 6 |
| どう作るかを決める（設計） | `design.md` | STEP 7 前半 |
| 作業に分ける | `tasks.md` | STEP 7 前半 |
| 仕様をもとに作る | `tasks.md` の「⚡ Start task」で1つずつ実装 | STEP 7 |
| 受け入れ条件で確かめて取り込む | ブラウザで ○／× を確認 → マージ | STEP 7 後半 |

つまり、**STEP 6〜7 の手順どおりに Spec を進めると、それだけで SDD をひと通り体験したことになります**。
文書は `.kiro/specs/＜Specの名前＞/` に保存されて GitHub に残るので、後から誰でも「何を作ろうとして、なぜこう作ったのか」をたどれます。

> **この回は表の上の2行（要件を作って、レビューで合意する）までを行います。**

## 手順

### 1. ブランチを確認して最新にする（5分）

1. 画面左下が `practice/自分の名前` になっていることを確認する
2. チャットで「最新の状態を取り込んで（pull して）」と頼み、表示されたコマンドを確かめて許可する

### 2. Spec を始める（10分）

1. Kiro パネル（おばけのアイコン）の **Specs** 欄の **「+」** を押す
2. 画面上部に「Enter your idea to generate requirement, design, and task specs.」という入力欄が開くので、次を貼り付けて **Enter** を押す（`自分の名前` は自分のローマ字に変える）

   ```
   exercises/step06-お題_変更依頼一覧ビューア.md の依頼をもとに、ツールの要件を作ってください。
   Spec の名前は change-request-viewer-自分の名前 にしてください。
   受け入れ条件は EARS 記法で書いてください。
   ```

   - この入力欄では `#` でファイルを選べないので、ファイルの場所（パス）をそのまま書いています
3. チャットに「どの進め方で始めますか？」（Input required）と出たら、**Requirements（要件から）** を選んで **Submit answer** を押す
   - Technical Design（技術設計から）や Quick Spec（まとめて自動生成）は選びません。この回は要件を自分で確かめるのが目的です
4. Kiro が `requirements.md` を作ります。ファイルを書き込む許可を求められたら、**許可** してください

### 3. 要件を読む（15分）

`.kiro/specs/change-request-viewer-自分の名前/requirements.md` が開きます。読んでみましょう。

- **ユーザーストーリー**：「○○として、△△したい。なぜなら□□だから」という形の要望
- **受け入れ条件（EARS 記法）**：「〜のとき、システムは〜しなければならない」という、合否を判定できる書き方

| EARS の型 | 例 |
|---|---|
| WHEN（〜したとき） | WHEN 利用者が CSV ファイルを選んだとき、THE システム SHALL 一覧を表に表示する |
| IF（もし〜なら） | IF CSV の列名が想定と違う場合、THE システム SHALL エラーメッセージを表示する |
| WHILE（〜の間） | WHILE 絞り込みが有効な間、THE システム SHALL 件数を絞り込み後の値で表示する |

> 英語の WHEN / SHALL が混ざっていても大丈夫です。日本語だけにしたいときは「受け入れ条件を日本語で書き直して」と頼みましょう。

### 4. AIに質問させて、要件を固める（25分）

依頼メールはあいまいなので、要件にも穴があるはずです。AIに質問させましょう。

```
この requirements.md に足りない観点や、依頼者に確認すべき点を、質問の形で挙げてください。
それぞれに「おすすめの答え」も付けてください。
```

1. 出てきた質問を読み、**自分が依頼者だったらどう答えるか** を決める
2. 答えをチャットで返す（例：「質問1は○○、質問3はおすすめどおりで」）
3. 「この答えを反映して requirements.md を更新して」と頼む
4. 更新された requirements.md を読み、納得できるまで 1〜3 を繰り返す（2〜3往復が目安）

> 依頼者に確認しないと決められないものは、自分で決めずに「未確定事項」として requirements.md の最後に残してもらいましょう。
> 「未確定事項の節を作って、そこに入れて」と頼めば OK です。

**ここで止める：** Kiro が「設計に進みますか？」と聞いてきても、今回は **進みません**。「今日は要件までで止めます」と返してください。

### 5. コミットしてプッシュする（10分）

1. チャットで次を送る

   ```
   作った requirements.md を「変更依頼一覧ビューアの要件を作成」というメッセージでコミットして、プッシュしてください。
   ```

2. Kiro が `git add`・`git commit`・`git push` などのコマンドを実行しようとして、許可を求めてきます
   - 表示されたコマンドに、自分のファイル（`.kiro/specs/change-request-viewer-自分の名前/`）や自分のブランチ名（`practice/自分の名前`）が入っていることを確かめてから許可する
   - `main` に直接送るコマンドや、意味の分からないコマンドなら、**許可せずに止まって**、「このコマンドは何をするものですか」とチャットで聞く

### 6. プルリクエストを出す（10分）

1. ブラウザで自分の GitHub のリポジトリ（`https://github.com/＜自分のユーザー名＞/kiro-handson-practice`）を開く
2. 黄色い帯の **「Compare & pull request」** を押す
   - 帯が出ていなければ、上部の **「Pull requests」** タブ → **「New pull request」** → compare に自分のブランチを選ぶ
3. 画面上部の行が **base: main ← compare: practice/自分の名前** になっていることを確かめる
   - **base repository が自分のリポジトリ（`＜自分のユーザー名＞/kiro-handson-practice`）になっているか** も確かめる。Fork でコピーした人は、公開元が選ばれていることがあるので、自分のリポジトリに選び直す
4. 次のように入力する
   - **タイトル**：`変更依頼一覧ビューアの要件`
   - **本文**：「要件を作りました。依頼者の目線で、足りない点や分かりにくい点を見直します。」
   - 右側の **Reviewers** は空欄のままでかまいません（自分のプルリクエストには、自分をレビュアーに指定できません）
5. **「Create pull request」** を押す

### 7. 要件を見直す（セルフレビュー）（20分）

ふつうは仲間にレビューしてもらう場面です。ひとりで進めるので、**Kiro にレビュー役をさせ**、そのうえで **自分でも GitHub の画面で見直します**。

**Kiro にレビュー役をさせる**

1. Kiro で新しいセッションを開き、次を送る（`taro` は自分の名前に）

   ```
   あなたは業務部門の依頼者です。#.kiro/specs/change-request-viewer-taro/requirements.md を、
   #exercises/step06-お題_変更依頼一覧ビューア.md の依頼を出した本人の立場で読み、
   「依頼の意図と違う点」「分かりにくい点」「抜けている点」をレビューコメントとして5つ挙げてください。
   対象のファイルは書き換えず、コメントは participants/taro/review-comments.md に保存してください。
   ```

2. 保存された `participants/自分の名前/review-comments.md` を開いて読む。このコメントは、STEP 7 の最初に要件へ反映します

**GitHub の画面で、自分でも見直す**

1. 自分のプルリクエストを開き、**「Files changed」** タブを押す
2. 気になる行の行番号の左にマウスを乗せ、出てくる **「+」** を押してコメントを書く
   - 例：「『担当者』は誰のことか、依頼者に確認する」
3. **「Add single comment」** を押す
4. あわせて [要件の見本](../examples/requirements-sample/requirements.md) と見比べ、気づいたことがあれば同じようにコメントしておく

> 仲間と進めている場合は、手順6の **Reviewers** で仲間を指定し、お互いのプルリクエストの「Files changed」でコメントし合います（仲間を自分のリポジトリに招待する方法は [勉強会で使うときのガイド](study-group-guide.md) にあります）。

> **今回はマージしません。** STEP 7 で同じブランチに設計と実装を足していき、最後にまとめて取り込みます。

## 困ったとき

- Specs 欄が見当たらない → Kiro パネル（おばけのアイコン）を開き直す
- 進め方を聞かれずに文書が作られ始めた → そのまま進めて大丈夫です。requirements.md ができたら「3. 要件を読む」へ進む
- Spec の名前が違うものになった → 気にしなくて大丈夫です。`.kiro/specs/` の下に自分のフォルダができていれば OK
- 要件がとても長くなった → 「今回は練習なので、要件を5個以内に絞って」と頼む
- 自分の名前ではない Spec フォルダがある → 触らないでください。自分の `change-request-viewer-自分の名前` だけで作業します
- プルリクエストの宛先（base repository）が公開元になっている → 自分のリポジトリを選び直す。公開元にはプルリクエストを出しません
